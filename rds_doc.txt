I. Overview
1. User Requirements
1.1 Actors


#
	Actor
	Description
	  1
	Guest
	An unauthenticated user who can explore, search, and filter the public music catalog, view public track details, and stream complete published tracks. After each track finishes, the system displays a login or registration prompt. A Guest cannot use authenticated features such as favorites, playlists, listening history, content upload, custom lyrics, or content reporting. 
	  2 
	Listener
	Authenticated general user. Has full access to advanced playback tools (queue, shuffle, repeat), manages playlists, writes personal (private) translated/transliterated lyrics, and uploads personal audio files to submit to the moderation queue. Additionally, receives and views system notifications regarding track moderation outcomes (approval or rejection with feedback reasons), report resolution updates, and platform announcements. 
	  3
	Staff
	Content management staff. Responsible for previewing and making approval/rejection decisions (with mandatory reasons) for songs uploaded by Listeners, as well as uploading and maintaining official lyric files. Additionally, receives real-time system notifications about incoming track submissions pending moderation and new content violation reports submitted by listeners. 
	  4
	Admin
	The highest-level system administrator. Has the authority to manage all accounts (role assignment, ban/unban), add/edit/delete core categories (such as Music Genres), and monitor system statistics.
	  5
	Email Service
	Automated email delivery system (Secondary Actor). Receives signals from the system to send welcome emails upon new account creation and distributes authentication codes/links during the password recovery flow.
	  6
	Cloud Storage
	Cloudinary cloud storage platform (Secondary Actor). Responsible for receiving, securely storing, and directly distributing multimedia files (MP3, cover art, avatars) to the user's browser, supporting byte-range data transmission techniques (HTTP Range Requests).

2.2 Screen Descriptions


#
	Feature / Use Case
	Screen Name
	Description
	1
	UC-01: Login
	Login
	Authenticates registered accounts across all operational roles (Listener, Staff, Admin) using email and password, granting role-appropriate system access.
	2
	UC-02: Register Account
	Register Account
	Allows Guests to register a new Listener account and automatically initiates the mandatory email verification process (Includes: UC-03).
	3
	UC-03: Verify Email
	Email Verification Result
	Validates single-use cryptographic tokens sent via email for newly registered account activation or password-reset authorization.
	4
	UC-04: Forgot and Reset Password
	Forgot and Reset Password
	Enables users to request a password-reset link via email, verifies the time-limited token, and securely configures a new account password (Includes: UC-03).
	5
	UC-05: Logout
	Logout Confirmation Dialog
	Safely terminates the current authenticated session across all roles, revokes active refresh tokens on the server, and returns the user to public browsing.
	6
	UC-06: View Recommended Song
	Explore Music (Public Home)
	Displays curated recommendations, trending tracks, new releases, active music genre tags, and featured albums for discovery on the home screen.
	7
	UC-07: View Ranking Board
	Top Charts (Ranking Board)
	Displays the platform leaderboard of published tracks ranked by aggregate streaming play counts, with genre filtering support.
	8
	UC-08: Filter Public Catalog

1. User Authentication 
1.1 UC-1: Login
UC ID and Name:
	UC-1 Login 
	Created By:
	DuyLH
	Date Created:
	26 /09/2026 
	Primary Actor:
	Guest 
	Secondary Actors:
	Email Service 
	Trigger:
	A guest enters their email address and password on the login screen and submits the form.
	Description:
	Authenticates a registered account, verifies whether the account belongs to a Listener or a Staff member, checks security conditions like email verification and account lockouts, creates a secure login session, and redirects the user to the correct page based on their role.
	Preconditions:
	PRE-1: The account has already been registered in the system.
PRE-2: The user is not currently logged in.
	Postconditions:
	POST-1: A valid login session is created and the user stays signed in.
POST-2: The account's last login time is recorded.
POST-3: Any previous failed login attempts are reset.
POST-4: The user is directed to the appropriate screen according to their role (Explore page for Listeners, Staff Dashboard for Staff, or Admin Dashboard for Administrators).
	Normal Flow:
	NF01: Successful login
1. The user opens the login page (the standard login page for Listeners, or the staff portal for Staff and Admins).
2. The user enters their email and password, chooses whether to keep "Remember Me" checked, and clicks Sign In.
3. The system checks the format of the email and ensures the fields are not left blank.
4. The system looks up the account by email, distinguishing between Staff and Listener accounts, and confirms that the user is logging in through the correct portal.
5. The system verifies that the password matches the account.
6. The system checks the account status: ensures the account is active, verified by email, not banned, and not currently locked out.
7. The system resets any failed attempt counters, marks the current login time, and issues a secure session token (valid for 30 days if "Remember Me" is selected, or 7 days by default).
8. The system signs the user in and redirects them to their designated home screen according to their role (AF05).
	Alternative Flows:
	AF01: Unverified email account
1. At step 6 of NF01, the system finds that the user has not verified their email address yet.
2. The system denies login and displays a notification with an option to resend the verification code.
3. The user requests a new code; the system sends a 6-digit verification code to their email and opens the code verification screen.


AF02: Staff and Admin login
1. A Staff member or System Administrator accesses the dedicated staff login portal.
2. At step 4 of NF01, the system recognizes the staff account and verifies their assigned role (Admin or Moderator).
3. Upon successful sign-in, the system redirects Admins to the Admin Dashboard and Staff to the Staff Dashboard.


AF03: Emergency account unlock via email OTP
1. When an account is temporarily locked after 5 failed password attempts (EX02), the system gives the user an option to unlock immediately by email.
2. The user clicks to request an unlock code; the system generates a 6-digit emergency OTP and emails it to the user.
3. The user enters the 6-digit OTP on the login screen and confirms.
4. The system validates the OTP, removes the temporary lock, resets the failed attempts, and allows the user to log in immediately.


AF04: Automatic lock expiration
1. The user waits out the 10-minute temporary lockout period.
2. When the user signs in again with the correct password, the system recognizes that the lockout period has passed, automatically unlocks the account, and logs the user in.


AF05: Role-based redirection
1. At step 8 of NF01, the system checks the user's role:
- A Listener is taken to the Explore music page.
- A Staff member or Moderator is taken to the Staff Dashboard.
- A System Administrator is taken to the Admin Dashboard.


AF06: Remember Me option
1. At step 2 of NF01, the user keeps the "Remember Me" checkbox checked.
2. The system extends the login session to 30 days so the user does not have to log in repeatedly.
	Exceptions:
	EX01: Incorrect credentials with warning countdown
1. At step 5 of NF01, the user enters the wrong password, or the email does not exist.
2. The system shows an error message without disclosing whether the email exists.
3. If the user fails 1 or 2 times, the system shows "Email or password is incorrect."
4. If the user fails 3 or 4 times, the system warns: "Incorrect password. You have N attempt(s) remaining before your account is temporarily locked for 10 minutes."
5. The user stays on the login page to try again.


EX02: Temporary account lock after 5 failed attempts
1. The user enters an incorrect password 5 times in a row.
2. The system temporarily locks the account for 10 minutes to protect against unauthorized access.
3. The system informs the user that the account is locked for 10 minutes and offers the option to unlock immediately via email OTP (AF03).


EX03: Banned or disabled account
1. At step 6 of NF01, the account has been banned or deactivated by an administrator.
2. The system denies login and displays a suspension notice advising the user to contact SoundWave support.


EX04: Logging in through the wrong portal
1. If a Listener attempts to log in through the Staff portal, the system blocks access and notifies them that the portal is reserved for Staff and Admins only.
2. If a Staff member attempts to log in through the Listener portal, the system rejects the attempt to keep administrative access separated.


EX05: Too many incorrect unlock OTP attempts
1. During the emergency unlock flow (AF03), the user enters the wrong 6-digit OTP 5 times.
2. The system deactivates the OTP code for security, requiring the user to wait and request a fresh code.


EX06: Service connection failure
1. The system cannot reach the database or the email delivery service.
2. The system informs the user that the service is temporarily unavailable and asks them to try again later.

3. The guest clicks "Register".

- If the email is completely new, the system proceeds to step 7.
- If the email is already in the system, it branches to AF01 (if already verified) or AF02 (if still unverified).

3. The system sends a security email to the address notifying them that a registration was attempted, with a link to log in or reset their password.
4. The screen shows the standard success message so attackers cannot detect whether the email is registered.


AF02: Email already registered but not yet verified
1. At step 6 of NF01, an account exists for this email but has not completed email verification.
2. The system checks whether 60 seconds have passed since the last code request.
3. If allowed, the system automatically sends a fresh 6-digit verification OTP to the email and directs the user to the verification screen.

UC ID and Name:
	UC-11 Control Playback
	Created By:
	HaoNTT
	Date Created:
	23/10/2026
	Primary Actor:
	Guest, Listener 
	Secondary Actors:
	None
	Trigger:
	A user interacts with playback controls (play/pause, seek slider, volume), track navigation buttons, queue controls, or playback modes on the active media player. 
	Description:
	Enables users (Guest and authenticated Listener) to control their active playback session, including pause/resume, timeline scrubbing (seek), volume adjustment, track navigation (next/previous), queue management, and mutually exclusive shuffle/repeat playback modes. 
	Preconditions:
	PRE-1: The user accesses the platform as a Guest or an authenticated Listener.
PRE-2: The media player has an active playing track or queued tracks available.
	Postconditions:
	POST-1: The media player and queue state immediately reflect the requested playback command. 
	Normal Flow:
	NF01: Basic playback control and timeline seeking
1. The user interacts with the media player to pause, resume, drag/click on the timeline seek bar, or adjust the volume slider.
2. The client-side media player validates the requested timestamp against the track duration boundaries.
3. The media player applies the new audio position immediately via direct HTTP Range Requests to the CDN and updates the elapsed time and interface indicators in real time.
NF02: Track navigation (Next / Previous)
1. The user clicks the Next or Previous track button on the media player.
2. The system identifies the target track within the active play queue.
3. The system invokes UC-10 (Play Music) to initialize and stream the new track.
NF03: Queue and playback mode management
1. The user opens the play queue drawer to inspect played/upcoming tracks, reorder items, remove a track, or toggle the Shuffle and Repeat modes on the media player bar.
2. The media player toggles the playback modes as mutually exclusive client-side settings:
1. Shuffle Mode: When enabled, automatically shuffles the upcoming tracks in the queue; when disabled, restores the original queue order.
2. Repeat Mode: When enabled, sets the current track to loop continuously upon completion.
3. The media player persists the active mode preferences in client session storage (sessionStorage) and highlights the corresponding button icons.
	Alternative Flows:
	AF01: Seek outside track duration
1. At step 1 of NF01, the user attempts to seek a time position beyond the track duration boundaries (<00:00 or >duration).
2. The media player automatically clamps the playback position to the nearest valid boundary (the beginning 00:00 or the end of the track).
3. The media player resumes playback from the clamped timestamp and returns to step 3 of NF01.
AF02: Previous track navigation (4-second rule)
1. At step 1 of NF02, the user clicks the Previous button.
2. If the current track has been playing for more than 4 seconds, the media player resets playback to the beginning (00:00) of the current track without switching tracks.
3. If the current playback duration is 4 seconds or less and no prior track exists in the queue, the media player resets playback to 00:00 and continues playing the current track.
4. If the current playback duration is 4 seconds or less and a prior track exists in the queue, the media player proceeds to step 2 of NF02 to navigate to and play the previous track.
AF03: Track completion and playback mode resolution
1. At step 2 of NF02, the currently playing track finishes.
2. If Repeat Mode is active: The media player resets audio playback to 00:00 and automatically replays the current track without advancing the queue.
3. If Repeat Mode is inactive: The media player advances to the next track (resolving the randomized next track if Shuffle Mode is active).
4. If the queue reaches the end and no upcoming tracks remain:
1. If the user is a Guest: The system halts playback and displays an authentication prompt modal inviting the user to Log In or Register (enforcing BR-11).
2. If the user is an authenticated Listener: The media player stops at the end of the track and retains the current player state.
	Exceptions:
	EX01: Media buffering / seek failure
1. At step 3 of NF01, an unexpected network disruption or CDN timeout prevents audio chunks at the seeked position from buffering.
2. The media player pauses playback, displays a non-blocking toast notification: "Unable to buffer audio at this position. Please check your network connection.", and restore the last stable playback position.
EX02: Target track becomes unavailable
1. At step 2 of NF02, the target track in the queue has been unpublished, hidden, or removed from the platform.
2. The system displays an error notification informing that the track is no longer available, automatically skips it, and advances to the next eligible track in the queue.
	Priority:
	Must Have 
	Frequency of Use:
	Very High 
	Business Rules:
	BR-11, BR-12 
	Other Information:
	Client-side State Management: Basic playback controls (play, pause, volume, timeline seek), playback modes (Shuffle, Repeat), and queue ordering are managed entirely on the client-side (via React session state, sessionStorage, and the HTML5 Audio API) without incurring backend API overhead.
- Queue Retention: Completed tracks remain in the active queue history rather than being removed, allowing listeners to seamlessly navigate back to previously played tracks using the Previous button. 
	Assumptions:
	The persistent media player bar remains accessible across different pages while the user browses the application.

The system uploads media assets to Cloudinary and saves the track into the database with an initial publication status of DRAFT. 
	Preconditions:
	PRE-1: The user is authenticated with an active account.
PRE-2: The user has prepared a valid audio file (MP3, WAV, or FLAC format, not exceeding 30MB). 
	Postconditions:

POST-2: A new track record containing synchronized lyrics data (if provided) is stored in the database with DRAFT publication status.

	NF01: Successful creation of a new track draft

2. The system displays the My Tracks dashboard with track status tabs and action controls.
3. The Listener clicks the "Create track" button.
4. The system navigates to the track creation screen and renders the upload form containing fields for title, genre selection, optional album assignment, description, lyrics upload and creation controls, and file upload zones for audio and cover artwork.
5. The Listener enters the track title, selects an active genre, uploads a valid audio file, optionally provides cover artwork, optionally attaches lyrics (by uploading an existing .lrc file or creating lyrics manually via AF02), and clicks the "Save as draft" button.
6. The system validates the input data to ensure mandatory metadata is provided (title, genre), and uploaded media files adhere to format and size limits.
7. The system uploads the audio file (and cover image if provided) to Cloudinary and retrieves secure HTTPS URLs along with audio duration.
8. The system generates a unique slug, initializes the track entity with DRAFT status including lyrics content, and persists the record into the database.
9. The system displays a success toast: "Draft saved successfully!" and redirects the Listener to the My Tracks screen. 
	Alternative Flows:

2. The system verifies album ownership, links the newly created track to the album, and updates the album track count upon successful persistence.

1. At step 3 of NF01, after uploading an audio file, the Listener clicks the "Create lyrics" button to create and synchronize lyrics manually using the LRC Maker tool.
2. The system opens the tool panel allowing the Listener to play the uploaded audio, input lyric lines manually, and tap keys to assign synchronized timestamps matching the rhythm of the music.
3. The Listener completes synchronization and clicks "Apply Lyrics", prompting the system to compile the synchronized text into standard LRC string format and attach it to the track before saving.


AF03: Handling unsaved changes upon clicking the Back button
1. At any point while editing form data, the Listener clicks the "Back" button on the screen header.
2. The system detects unsaved changes and prompts a confirmation pop-up modal asking whether the user wants to save the draft, presenting three distinct actions: "Save", "Don't Save", and "Cancel".
3. If the Listener selects "Save", the system validates inputs and saves the draft by executing steps 4 through 7 of NF01 before navigating the user back to the My Tracks screen .
4. If the Listener selects "Don't Save", the system discards all entered form data and uploaded assets without saving, immediately returning the Listener to the My Tracks screen.
5. If the Listener selects "Cancel", the system dismisses the pop-up modal and keeps the Listener on the Upload Track screen to continue editing.

1. At any point before saving the form, the Listener explicitly clicks the "Cancel" button at the bottom of the form.

	Exceptions:
	EX01: Missing mandatory fields or invalid inputs
1. At step 4 of NF01, the track title is blank, no genre is selected, or no audio file is attached.
2. The system halts the upload process, highlights invalid fields in red, preserves existing inputs, and displays an inline validation error message.


EX02: Invalid media file format or size exceeded
1. At step 4 of NF01, the audio file exceeds 30MB (or has an unsupported format), or the cover image exceeds 5MB (or is not JPG/PNG).
2. The system prevents submission, displays a file size/format error alert beneath the affected field, and prompts the user to select an eligible file.


EX03: Invalid lyrics file format
1. At step 4 of NF01, the uploaded lyrics file exceeds 1MB or has an invalid file extension (not .lrc).
2. The system rejects the lyrics file and displays an error alert asking the user to provide a valid .lrc file or create lyrics manually.

1. At step 5 of NF01, the system fails to upload media files to Cloudinary due to network timeouts or cloud downtime.
2. The system aborts the transaction, prevents orphan database entries, logs the error, and displays an alert: "Failed to upload media to cloud storage. Please check your connection and retry."


EX05: Database persistence failure
1. At step 6 of NF01, the database fails to insert the new track record.
2. The system purges the newly uploaded media files from Cloudinary, rolls back the transaction, and displays a system error notification.

	Must Have 
	Frequency of Use:
	High 
	Business Rules:
	BR-18, BR-21, BR-23, BR-36 
	Other Information:

10.4 UC-19.4 Delete A Track
UC ID and Name:
	UC-19.4 Delete Track 
	Created By:
	TuanTA
	Date Created:
	26/09/2026 
	Primary Actor:
	Listener   
	Secondary Actors:
	Cloud Storage 
	Trigger:
	The Listener clicks the "Delete" button on the Track Details view and confirms the action in the confirmation modal. 
	Description:
	Allows an authenticated creator to delete an owned track in DRAFT, REJECTED, or PUBLISHED status through the Track Details view. Tracks currently queued for Staff moderation (PENDING) are strictly locked and cannot be deleted. The system applies a dual-tier deletion strategy: unapproved tracks (DRAFT and REJECTED) undergo permanent removal (Hard Delete) from PostgreSQL, while published tracks (PUBLISHED) undergo soft deletion (Soft Delete) by transitioning the status to TAKEN_DOWN. In both cases, media assets on Cloudinary are purged to release cloud storage and prevent unauthorized listening. 
	Preconditions:
	PRE-1: The user is authenticated in the system with the Listener (Creator) role.
PRE-2: The user is accessing the Track Details view of an existing track owned by the currently authenticated user.
PRE-3: The target track is in DRAFT, REJECTED, or PUBLISHED status (rendering the Delete action button active).
	Postconditions:
	POST-1: Cloud media assets (audio file and cover artwork) are purged from Cloudinary storage.
POST-2: If the target track was in DRAFT or REJECTED status, the track record and associated draft data are permanently deleted from the PostgreSQL database.
POST-3: If the target track was in PUBLISHED status, the track's publication status is updated to TAKEN_DOWN, revoking public streaming access while preserving referential integrity for listening history and analytics.
POST-4: If the track belonged to an album and no other published tracks remain in that album, the album status is automatically downgraded to DRAFT.
POST-5: The deleted or taken-down track is filtered out of the creator's active My Tracks table, and the system navigates the creator back with a success confirmation.
	Normal Flow
	NF01: Delete an owned track successfully:
1. On the Track Details view, the Listener clicks the Delete button to initiate track removal.
2. The system displays a confirmation modal stating the consequences of deletion and requesting confirmation.
3. The Listener clicks the Confirm Delete button in the modal.
4. The system validates the authentication session, verifies track ownership, and confirms the track is in an eligible lifecycle status.
5. The system requests Cloudinary to permanently purge the hosted audio file and cover image associated with the track.
6. The system checks the publication status of the target track.
7. For a track in DRAFT or REJECTED status, the system deletes all temporary associations and permanently removes the track record from PostgreSQL.
8. For a track in PUBLISHED status, the system updates the publication status to TAKEN_DOWN, clears public media streaming URLs, and persists the soft-deleted state in PostgreSQL.
9. If the track was assigned to an album, the system evaluates the remaining tracks in the album and updates the album status to DRAFT if no published tracks remain.
10. The system closes the confirmation modal, navigates the creator to the My Tracks view, and displays a success notification confirming the track was removed.
	Alternative Flows:
	AF01: Cancel track deletion
1. In the confirmation modal, the Listener clicks Cancel or closes the dialog.
2. The system dismisses the modal and retains the stored track state on the Track Details view.


AF02: Album status downgrade upon track removal
1. The track selected for deletion was the sole published track within a published album.
2. After the track is removed or transitioned to TAKEN_DOWN, the system automatically reverts the parent album's status from PUBLISHED to DRAFT.
	Exceptions:
	EX01: Deletion of pending track denied
1. The system detects that the target track is currently in PENDING status awaiting Staff moderation review.
2. The system locks the delete control, rejects the request with a forbidden operation error, and notifies the creator that pending submissions must be withdrawn before deletion.


EX02: Unauthorized access or unowned track
1. The system detects that the track identifier does not exist or does not belong to the currently authenticated user.
2. The system denies the operation and returns an access denied error.


EX03: Cloud media purge failure
1. The request to purge audio or cover assets from Cloudinary encounters a network timeout or third-party service interruption.
2. The system logs the cloud failure silently to ensure that database record deactivation or removal completes cleanly without leaving dangling or locked transactions.
	Priority:
	Must Have
	Frequency of Use:
	Medium
	Business Rules:
	BR-21, BR-23, BR-09, BR-36 
	Other Information:
	Sub-function of UC-19 Manage My Tracks. Deletion is initiated strictly through the Delete button on the Track Details view. Hard deletion is applied to unapproved content (DRAFT, REJECTED), whereas soft deletion (TAKEN_DOWN) is applied to published content (PUBLISHED) to preserve referential data integrity. 
	Assumptions:
	The creator holds the legitimate authority to delete or take down the uploaded musical work.

2. The system validates that the album currently contains more than one track.
3. The system displays a confirmation dialog: "Are you sure you want to delete this track? The album will remain intact."
4. The Listener confirms deletion.
5. The system deletes the single track record, purges its audio from Cloud Storage, and recalibrates the album track count.
6. The system displays a success toast ("Track deleted successfully") and refreshes the album detail view.
	Exceptions:

EX04: Attempting to delete the last remaining track in an album
1. At step 2 of AF02, the album contains only one constituent track.
2. The system blocks deletion, displays an error alert ("An album must contain at least one track. To remove all tracks, please delete the album instead"), and keeps the track intact.
	Priority:
	Must Have

3. The system prompts Staff to select or enter a mandatory rejection reason explaining the issue.
4. Staff enters feedback (e.g., "Lyrics desynchronized after 00:45; please re-align timestamps") and confirms.
5. The system marks the submission as REJECTED; the live track retains its existing lyrics unchanged.
6. The system dispatches an alert with the rejection reason to the uploader so they can revise and resubmit. 
	Exceptions:
	EX01: Empty rejection reason
1. Staff clicks confirm reject without providing a reason.
2. The system blocks the rejection action and requires descriptive feedback to ensure transparency.  
	Priority:
	Must Have  
	Frequency of Use:
	Medium 
	Business Rules:
	BR-20, BR-25, BR-38
	Other Information:
	Staff inspection tool includes playback scrubbing and single-line auditioning for rapid verification. 
	Assumptions:
	Audio streaming is available in the staff inspection tool.

IF @userId IS NOT NULL
BEGIN

    IF EXISTS (SELECT 1 FROM tracks WHERE id = @trackId AND publication_status = 'PUBLISHED')

IV. Appendix
1. Assumptions & Dependencies
AS-1: The user must have a stable internet connection with a minimum speed of 1Mbps to ensure uninterrupted audio streaming.
AS-2: All audio files uploaded by creators are assumed to be legally owned or appropriately licensed, minimizing copyright liabilities for the platform.
DE-1: The platform relies heavily on a third-party Cloud Storage provider (e.g., AWS S3, Google Cloud Storage, or Firebase) for hosting and streaming large MP3 audio files and image assets.
DE-2: The system's email verification and password recovery functionalities depend entirely on an external SMTP Email Service (e.g., SendGrid, Mailgun).
2. Limitations & Exclusions
Offline Playback: The current scope of the project does not support downloading songs for offline listening. Users must be online to stream music.
Mobile Application: The platform is designed strictly as a responsive web application. A native mobile app (iOS/Android) is excluded from this phase.
Monetization/Payment: The platform will operate entirely free of charge. Subscription plans, payment gateways, and creator royalty payouts are not included in the initial release.

	Audio streaming is executed via direct HTTP Range Requests between the client's HTML5 Audio player and the Cloud Storage (Cloudinary) CDN. The backend application server is responsible only for verifying track playback authorization and returning the secure CDN URL; it does not proxy audio binary streams.
